# Testing Strategy

General principle across every subsystem: business/decision logic is isolated from Kubernetes and network glue code so it's unit-testable on its own. Integration tests then prove the glue code actually works against a real cluster. Neither layer substitutes for the other.

## Operator

- **Unit tests:** the phase table lives in `operator/internal/lifecycle` with no Kubernetes dependency, and every documented transition, every rejected/conflicting transition, and the terminal `Failed` phase has a plain Go test there. The reconciler is tested with `envtest` (real API server, no controllers) in `operator/internal/controller`: provisioning and owner references, unsupported engine, idempotency, scaling, backup, restore, finalizer draining, and the scale-during-backup collision, which asserts on the PVC's actual spec and the Job's state rather than on `status.phase`. Run with `make test` in `operator/`.
- **Integration tests:** `TestTenantDatabaseLifecycle` in `operator/test/integration` (build tag `integration`) runs the manager in-process against the current kubeconfig context, a real `kind` cluster in CI. It provisions Postgres, loads rows through `psql` inside the pod, holds a backup Job open through the injected backup command, scales mid-backup, and asserts the PVC does not change until the Job completes, that the row count is unchanged afterwards, and that a restore from that dump brings back deleted rows; then it points the unmodified backup script at a database that does not exist so a real `pg_dump` exits non-zero, and asserts from the Job pod's exit code and the CR that the operator returns `Backing Up -> Ready` with `BackupFailed`, a Warning event, an unchanged `lastBackupTime` and intact data. Run with `make test-integration`; CI runs it on the same five-node `kind-config.yaml` as every other job. On failure it dumps Job logs, the database log, readiness transitions, cluster-wide warning events, node conditions and kube-proxy/kindnet logs; that dump is how the Service-selector bug (Job pods selected as database endpoints) was found in CI.

## Provisioning/GitOps

- **Unit tests:** Crossplane composition rendering tested with `crossplane render` against `gitops/compositions/examples/databaseclaim.yaml`, asserting the composed `TenantDatabase` carries the platform defaults, the requested storage, and the tag labels (CI job `gitops-unit`; locally the CLI needs Linux and Docker, so run it in WSL). The admission rules are tested offline with `kyverno test gitops/policies/tests`: one good and one at-ceiling claim pass, every violation class fails, and the direct `TenantDatabase` ceiling is covered both ways.
- **Integration tests:** `TestPhase2PolicyAndGitOps` in the `e2e/` module (build tag `e2e`) runs against a cluster bootstrapped from `gitops/argocd` (CI job `platform-e2e`). It reads the Kyverno webhook's `failurePolicy` from the cluster, applies violating claims and a violating `TenantDatabase` directly and asserts nothing exists afterwards, then pushes a throwaway branch `e2e/<run>` of this repository holding one valid and one violating claim and points temporary ArgoCD Applications at it: the valid claim must become a `TenantDatabase` with the composed spec, the violating one must fail the sync at admission with no object created. Drift is then introduced live: a claim edit must show OutOfSync and stay unreverted (stateful class), and weakening a policy's `validationActions` must be reverted by selfHeal (stateless class). The branch and Applications are removed at the end.

## Scheduler plugin

- **Unit tests:** the scoring function is pure (no cluster I/O) in `scheduler-plugin/internal/scoring` and tested in isolation against synthetic cluster states, covering the cost/fragmentation/preemption-risk tradeoff explicitly, including the edge cases: all nodes spot (a latency-sensitive pod is unschedulable rather than placed), no spot capacity (equal costs leave fragmentation to decide), latency-sensitive workload present (spot nodes filtered before scoring), the cheap-spot-wins-even-at-maximal-risk case that pins the weighting, GPU stranding, and score bounds. `internal/pricing` covers the node-label contract and the AWS source against fakes; `internal/plugin` covers the framework adapter (Filter, PreScore, Score, args). Run with `make test` in `scheduler-plugin/`.
- **Performance tests:** upstream `scheduler_perf` is not importable, so `scheduler-plugin/test/perf` (build tag `perf`, `make bench`) reproduces its method: a real kube-apiserver from envtest, the real scheduler in-process with a default profile and the kiln profile side by side, 200 synthetic nodes, a burst of 500 pods per profile, and creation-to-bind latency measured through a watch. It reports p50, p99 and pods/s for both profiles so any degradation from the custom scoring is a number, alongside `BenchmarkScore` for the pure function at 100/1000/5000 nodes.
- **Exit-criterion replay:** `TestPhase3SchedulerCostReduction` in the `e2e/` module (build tag `e2e`, CI job `platform-e2e`) builds one seeded trace of 60 pods (20% latency-sensitive, 40% standard, 40% batch, three sizes, 30 to 60 second sleeps, two-second arrivals) and replays it first through `default-scheduler` and then through `kiln-scheduler` on the same five-node kind cluster. Each run is billed from the API server's record alone: every pod's node and its container's actual start and finish times, merged per node, so a node is charged its hourly-cost label for every second it hosts at least one trace pod (node-occupancy instance-hours, `METRICS.md`). The test asserts kiln-scheduler bills strictly less than the default and that no latency-sensitive pod ran on a spot node, and logs the percentage. The plugin's own score is never read.
- **Manual validation, outside CI:** the AWS price source is tested against fakes. To confirm the fakes still mirror the real APIs, run once locally with AWS credentials in the standard credential chain (a few read-only `DescribeSpotPriceHistory` calls and one public S3 fetch, trivial cost):

  ```
  cd scheduler-plugin && go test -tags=liveaws ./internal/pricing/aws/ -run Live -v
  ```

  It is excluded from every default `go test` invocation, never runs in CI, and is not part of Phase 3's exit criterion.

## Progressive delivery controller

- **Unit tests:** the decision lives in `delivery-controller/internal/analysis` with no Kubernetes, Istio or Prometheus imports. Plain tests pin every rule: the sample-size gate, capped per-window evidence (a flagrant regression takes exactly three windows), the CUSUM floor, checkpoint acceptance and reset, anomaly hold-and-halve, promotion only after the last checkpoint is accepted, Inconclusive and MetricsUnavailable timeouts. The simulation suite drives 1000 seeded rollouts per class at 200 rps in 15 s windows with checkpoints 5/20/50/100 and minSampleSize 500: healthy (0.1%, 0.3%, 0.5% errors) must promote; degrading (step to 30%, step to the 2% regression point, a ramp from 0.5% to 3% over eight windows, a 5% latency tail) must roll back in at least 90% of runs; noisy-but-healthy (steady at 70% and 90% of the limit, Beta-distributed bursty windows averaging 80% of the limit, one window at ten times the limit) must stay under the 5% false-rollback ceiling. Measured on the committed suite: healthy 100% promoted in about 2m30s; the flagrant step rolled back 100% within 30 s of onset, the 2% step 100% (p95 2m30s), the ramp 100%, the latency tail 100% within 45 s; noisy 0.1%, 0.4%, 2.8% and 0% false rollbacks. `internal/metrics` covers Istio counter reads, bucket interpolation and counter resets against an in-process fake Prometheus; `internal/mesh` covers the VirtualService writer against a fake client; `internal/controller` runs the reconciler under `envtest` with a schema-less stand-in VirtualService CRD and a scripted metric source, asserting on the VirtualService weights, Deployment specs, owner references and events: initialization, regression rollback, no retry of a rolled-back version, promotion through every checkpoint, restart on a mid-rollout template change, the metrics-unavailable timeout, and an invalid step schedule. Run with `make test` in `delivery-controller/`.
- **Integration tests:** `TestPhase4ProgressiveDelivery` in the `e2e/` module (build tag `e2e`, CI job `platform-e2e`) runs against the ArgoCD-bootstrapped cluster with Istio, Prometheus and the deployed controller; it waits for all three, because the first CI run had no Prometheus and the controller correctly never shifted traffic, which the test could not explain at the time. In a fresh `istio-injection=enabled` namespace it deploys a fortio server behind a Service, a meshed fortio load generator at 100 qps and a `CanaryRollout` with checkpoints 20/50/100 and minSampleSize 200. It first proves the initial state (VirtualService 100/0, primary available, target parked, a 10 s load run exec'd inside the meshed client returns under 1% errors), then rolls out a version answering 30% of requests with 500 and asserts, from the mesh and the pods only: the VirtualService reaches 20% canary and canary pods exist, then the VirtualService returns to 100/0, the target is at zero replicas, no canary pods remain, primary pods still run the original arguments and are Ready, and a fresh load run is under 1% errors. Then it rolls out a version answering 0.5% with 500, records every canary weight the VirtualService shows, requires 20, 50 and 100 plus at least one confidence-sized sub-step, and asserts primary pods run the new arguments and are Ready with the canary gone and a fresh load run under 2%. Both transitions are also measured across the flip itself: an uninterrupted fortio run from the meshed client starts before the VirtualService goes back to 100% primary and outlasts the drain grace, and it may contain no connection failure and no Envoy 503 at all (the version's own 500s are bounded), while the canary pods must outlive the flip by the grace. The CR's phase and reason are logged and cross-checked last; they are never the evidence. Measured locally on the five-node kind cluster: rollback 44 s after the split began, promotion 2m24s after the rollout began with weights 20, 41, 43, 50, 76, 100, whole test about four minutes.

## Chaos/resilience module

- **Unit tests:** the abort and score logic (`chaos/internal/analysis`) is pure Go, tested against synthetic scrape streams with no cluster or fault mechanism in sight: a healthy stream never aborts; a stream that crosses the error bound or the latency tail aborts on the first breached window; windows below the sample floor merge; silence past the metrics timeout aborts as blind, and a transient outage under it does not; recovery completes on the first clean post-fault window and gives up after the configured windows; and the score is checked across headroom-and-recovery combinations. The fault injectors (`chaos/internal/fault`) are tested against a recording executor: `tc` and `iptables` commands run inside the pod's namespace, revert is idempotent (a missing qdisc or chain is the reverted state, a real error surfaces), a partition keeps loopback and the node reachable, the container PID is resolved from a fake `/proc`, and the ledger round-trips. The agent's scope logic (`chaos/internal/agent`) is tested directly: the cap floors and never rounds up, and an over-selection is contained to the cap deterministically.
- **Integration tests (envtest):** the controller and the agent run together against an API server, with a scripted metric source and a recording injector standing in for the fault mechanism, so the whole loop is exercised in process. It proves a cross-namespace target and a zero-flooring cap are rejected before injection; a healthy experiment scores high and every fault is reverted; a forced breach aborts and the agent reverts each faulted pod; lost metrics abort rather than inject blind; the cap is never exceeded and holds for the life of the fault; resource-exhaustion needs a CPU limit; pod-kill deletes pods while the agent injects nothing; and a deleted experiment is held by its finalizer until the lease lapses. Ground truth is the recording injector, never the CR's status.
- **End-to-end (`TestPhase5Chaos`, `platform-e2e`):** against the ArgoCD-bootstrapped cluster with Istio, Prometheus, the chaos controller and the agent DaemonSet, in a fresh `istio-injection=enabled` namespace with a four-replica fortio target and a meshed load generator. All four faults run. Blast-radius containment is asserted from the node: the `iptables` DROP chain appears only inside the targeted pods' network namespaces, never a pod outside the cap. The forced breach is a 2000 ms latency injection against a 1000 ms p99 limit; the test reads the `tc netem` qdisc inside the pod's namespace directly (via `crictl` and `nsenter` on the kind node), confirms the fault auto-aborts, and confirms the `netem` is gone from every targeted pod within the bound. Pod-kill is proven by pod UIDs disappearing and then holding stable after the experiment ends. The CR's phase and score are read last, never as the proof. On kind the resource-exhaustion cgroup join is environment-specific, so the end-to-end test asserts that experiment runs and scores while the burner mechanics are covered by the unit tests.

## Audit/RBAC service

- **Unit tests (JUnit/Mockito, `./gradlew test` in `audit-service/`):** the hash and its canonical input (`HashChain`) are pure: a known-answer test pins one entry's hash including the sorted-key canonical `details` and the microsecond timestamp format, a chain of three verifies, and a change to any field or to `prevHash` is detected. The idempotency decision (a unique-constraint violation on `eventId` is acknowledged and counted, never retried or stored) and the role mapping from the JWT `roles` claim to the three endpoints are tested with no Kafka or Postgres present.
- **Integration tests (Testcontainers, `./gradlew integrationTest`, CI job `audit-integration`):** a real Kafka and a real Postgres per run. Events are published to the topic and the rows are read back over plain JDBC, never through the service's endpoints; the chain is asserted from those rows. Redelivery is simulated by re-publishing one record byte-for-byte and asserting the row count is unchanged and the duplicate counter moved. Tampering is simulated by an `UPDATE` of one row's `actor` as the superuser and asserting `GET /v1/audit/verify` reports `AUDIT_CHAIN_BROKEN` naming that `seq`. Tokens are minted from a key pair generated inside the test; 401 without a token and 403 without the role are covered.
- **Publishers (Go):** the shared `audit` module is tested against an in-process fake broker (`kfake`): the wire shape is the documented one, delivery is keyed by resource, and `Publish` never blocks with an unreachable broker, reporting buffer-full and invalid events through `OnFailure` (ADR-0017). Each controller's existing envtest suite gains assertions on an `audit.Recorder` that the expected action, outcome, resource and actor are published at the transition, and that a repeated transition republishes the same deterministic `eventId`.
- **End-to-end (`TestPhase6Audit`, `platform-e2e`):** against the ArgoCD-bootstrapped cluster with Kafka, the audit Postgres, the audit service and every publishing controller deployed, including the operator. It submits a `DatabaseClaim` through `POST /v1/requests` and drives it through provision, backup, restore and scale; submits a violating claim and requires `422 POLICY_DENIED`; binds a pod through `kiln-scheduler`; runs the Phase 4 broken-version rollback and the Phase 5 pod-kill experiment in their own mesh namespaces. Visibility is then read from the broker pod (`kafka-console-consumer` from offset zero) and from the Postgres pod (`psql` over the local socket), never from `GET /v1/audit`: every expected action, outcome and resource must be on the topic and in the table exactly once, with the caller's subject as `actor` on the claim, the composed `TenantDatabase` and every operator action, which proves the annotation travelled through the composition. The chain is recomputed in the test from the rows per `DATA_MODEL.md` before `/v1/audit/verify` is asked to agree. Tampering is a `psql UPDATE` of one row's `actor`, and both the recomputation and the endpoint must name that `seq`; the row is restored afterwards. Redelivery re-produces the captured record byte-for-byte with `kafka-console-producer`, requires the topic to hold it twice, and requires the row count for that `eventId` to stay at one with the chain intact. The write boundary is checked with `SubjectAccessReview`s: each controller's ServiceAccount can list its own kind and none can read the `audit-postgres` Secret.

## Cross-cutting

- CI runs the full unit test suite on every push; integration tests (anything requiring `kind`, Testcontainers, or a live Istio install) run on merge to main and nightly, given their longer runtime.
- Every subsystem's exit criterion in [`ROADMAP.md`](ROADMAP.md) is written to be provable by a specific test named in this document, not by manual click-through verification.
